数据库表设计：从业务建模到数据完整性 ​

1. 如何设计一张表 ​

我们应该从真实的业务场景出发。比如需要设计一个“用户登录”功能，那么可以先设计一个 users 表，包含 id、account、password_hash 等字段；其中 users.id 可以作为 orders 表的外键。

从这个例子可以看出，数据库设计应该从业务开始思考：需要哪些表、每张表有哪些字段，以及表与表之间通过哪些字段建立关系。

2. 常见的五种约束 ​

约束的作用是保证数据的正确性和完整性，为字段或数据之间的关系设置规则。

2.1 五种常见的数据库约束 ​

约束中文名称主要作用
PRIMARY KEY主键约束唯一标识一条数据
FOREIGN KEY外键约束保证表之间的引用有效
UNIQUE唯一约束防止字段值重复
NOT NULL非空约束不允许字段为 NULL
CHECK检查约束限制字段值满足指定条件

主键约束 ​

主键具有以下性质：

  • 唯一：不能重复。
  • 非空：不能为 NULL。

一张表只能有一个主键约束，但主键可以由多个字段组成，也就是联合主键。

外键约束 ​

例如订单表：

id（主键）user_id（外键）
1011
1021
1032

其中 orders.user_id 引用了 users.id。如果尝试插入一个不存在的用户：

sql
INSERT INTO orders (id, user_id)
VALUES (104, 999);

因为 users 表中没有 id = 999 的记录，这次插入会失败。外键可以保证引用的数据确实存在。

唯一约束 ​

例如用户表：

idaccount（UNIQUE）
1zhangsan
2lisi
3wangwu

将 account 设置为唯一约束后，就不能再次注册已经存在的账号。

非空约束 ​

非空约束要求字段必须有值：

sql
account VARCHAR(64) NOT NULL

需要注意：

  • NULL 表示缺少值，并不等于空字符串。
  • '' 表示长度为 0 的空字符串。
  • NOT NULL 只能限制 NULL，不能限制空字符串；如果业务上也不允许空字符串，还需要配合 CHECK 约束。

检查约束 ​

检查约束可以限制字段值必须满足某个条件。例如套餐价格不能为负数：

sql
price_fen BIGINT CHECK (price_fen >= 0)

3. 自增主键与并发安全 ​

数据库开发中常见的并发问题是：即使注册发生在不同时间，只要两个请求的查询和插入过程发生重叠，就可能产生冲突。

采用 Java 后端生成用户 ID 的方案确实可行，但如果生成策略不完善，可能产生主键冲突。更稳妥的做法是让数据库负责生成主键。

3.1 为什么数据库自动生成更好 ​

PostgreSQL 可以通过 GENERATED ... AS IDENTITY 自动生成主键：

sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account VARCHAR(64) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL
);

数据库能够在并发插入时协调主键生成，避免应用层通过“查询最大 ID 再加一”这类方式造成竞争。

3.2 删除后的 ID 是否应该复用 ​

如果删除了 id = 2 的用户，之后新用户注册时，通常应该继续生成新的 ID，而不是重新使用 2。

如果重复利用旧的主键，历史订单或其他关联数据可能被错误地连接到新用户。主键更适合作为记录的稳定标识，而不是连续编号展示给用户。

4. 数据库安全 ​

用户密码应该经过专门的密码哈希算法处理后再存入数据库。

这里需要区分哈希（hash）和加密（encryption）：

  • 加密：通常可以使用密钥解密，还原原始数据。
  • 哈希：通过算法生成摘要，设计目标不是直接还原原文。

密码场景应该使用适合密码存储的算法，例如 BCrypt 或 Argon2id。登录时，系统使用用户输入的密码和数据库中的哈希值进行验证，而不是尝试“解密”出原密码。

5. 外键删除规则 ​

PostgreSQL 外键常见的删除规则如下：

规则行为适合场景
NO ACTION存在违反外键约束的引用时拒绝操作（默认）默认保护关联数据
RESTRICT存在引用时立即阻止删除严格限制父记录删除
CASCADE自动删除所有关联的子记录确实需要连带删除的从属数据
SET NULL将子表对应外键设为 NULL允许子记录脱离父记录
SET DEFAULT将子表对应外键设为默认值存在有效默认管理值的场景

5.1 ON DELETE RESTRICT ​

sql
FOREIGN KEY (user_id)
REFERENCES users (id)
ON DELETE RESTRICT

删除用户时，如果该用户仍然存在订单，数据库会阻止删除操作。

5.2 ON DELETE CASCADE ​

sql
FOREIGN KEY (user_id)
REFERENCES users (id)
ON DELETE CASCADE

删除用户时，数据库会自动删除关联订单。这个规则适合生命周期完全依附于父记录的从属数据，使用前需要确认级联范围。

5.3 ON DELETE SET NULL ​

sql
FOREIGN KEY (user_id)
REFERENCES users (id)
ON DELETE SET NULL

用户被删除后，订单仍然保留，但订单中的 user_id 被设置为 NULL，表示订单不再关联该用户。使用这种规则时，外键字段必须允许 NULL。

6. 物理删除和逻辑删除 ​

6.1 物理删除 ​

物理删除是真正从数据库中删除一条记录，特点包括：

  • 数据库不再保存该行。
  • 通常无法直接恢复。
  • 外键可能阻止删除，也可能触发级联删除。
  • 记录占用的空间需要数据库后续维护才能重新利用。
  • 物理删除不代表备份、WAL 等历史介质中的数据会立即消失。

6.2 逻辑删除 ​

逻辑删除不真正删除记录，而是修改一个字段，表示这条记录已经被删除或停用。例如使用 account_status 表示账号状态：

  • ACTIVE：正常使用。
  • BANNED：管理员封禁。
  • DELETED：账号已注销。

对于订单、支付流水、审计记录等需要长期追溯的数据，逻辑删除通常更容易保留历史上下文。

不推荐随意使用物理级联删除：如果之后需要核对流水、审计操作或分析客户行为，级联删除可能让历史记录难以追踪。

7. 事务 ​

事务是把多个数据库操作捆绑成一个整体：要么全部成功，要么全部失败，不允许只完成其中一部分。

只有事务成功时才提交；如果执行过程中失败，就回滚已经执行的操作。

7.1 事务的三个基本操作 ​

在 PostgreSQL 中，需要认识三个关键字：

SQL含义
BEGIN开始事务
COMMIT提交事务
ROLLBACK回滚事务

例如转账操作：

sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;

如果任意一步失败，就应该执行 ROLLBACK，避免只扣款而没有完成收款。

7.2 事务的四大特性（ACID） ​

  • A：Atomicity，原子性 —— 一个事务中的操作要么全部成功，要么全部失败。
  • C：Consistency，一致性 —— 事务执行前后，数据库都必须满足约束和业务规则。
  • I：Isolation，隔离性 —— 并发执行的事务之间按照隔离级别控制相互影响。
  • D：Durability，持久性 —— 事务提交成功后，数据库应保证已提交的数据持久保存。

8. 订单快照 ​

历史订单应该保存交易发生时的数据，而不能完全依赖随时可能改变的商品或套餐信息。

例如，订单表可以增加以下快照字段：

sql
plan_name_snapshot VARCHAR(128) NOT NULL,
duration_days_snapshot INTEGER NOT NULL

即使套餐名称、价格或时长后来发生变化，历史订单仍然可以展示当时交易使用的内容。

9. UUID ​

UUID（Universally Unique Identifier）是通用唯一识别码。

它的常见特点包括：

  1. 不需要先查询数据库，应用可以直接生成。
  2. 在合理使用的前提下，重复概率极低。
  3. 相比连续数字 ID，更难从标识符推测数据规模或记录顺序。

UUID 可以用于幂等键、避免重复下单、外部资源标识以及凭证构建等场景。不过它的存储空间和索引性能特征与整数主键不同，应该根据业务规模和数据库特性选择。
